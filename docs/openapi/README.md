# OpenAPI: модуль user

- `user.yaml` — самостоятельная спецификация модуля, OpenAPI 3.1.0.
- `openapi.yaml` — общая точка входа со ссылками на `user.yaml`, без дублирования схем. При использовании этой точки входа оба файла должны быть доступны рядом.

Реализация API не изменялась. Других спецификаций OpenAPI на момент анализа в проекте не найдено.

## Покрытие

В текущем модуле объявлены две REST-операции:

| Метод | Путь контроллера | operationId | Авторизация |
| --- | --- | --- | --- |
| GET | `/api/v1/clients/me/profile` | `getClientProfile` | Bearer JWT |
| PUT | `/api/v1/clients/me/personal-info` | `updatePersonalInfo` | Bearer JWT |

С учётом `server.servlet.context-path` и порта из локального `application.yaml` полный URL: `http://localhost:8081/carhub/api/v1/clients/me/profile`.

Контроллер не принимает path/query-параметров и пользовательских заголовков. GET не имеет тела, PUT принимает обязательный `UpdatePersonalInfoRequest` с `@Valid`. Идентификатор пользователя берётся из `sub` JWT. Заголовок `Authorization` описан через `components/securitySchemes`, а не как параметр операции. Проверки ролей и scopes не заданы.

В схемах отражены DTO ответов, `UpdatePersonalInfoRequest` и оба используемых enum. Поля records присутствуют в сериализованном ответе, включая поля со значением `null`. Отсутствующий документ представлен `null`, а не пустым объектом.

PUT используется для заполнения и редактирования персональных данных. Все поля (`firstName`, `lastName`, `middleName`, `birthDate` и `phoneNumber`) обязательны. Отсутствие отчества, `null` или пустое значение отклоняются; без отчества секция `PERSONAL_INFO` считается незаполненной. Имена сохраняются после `String.strip()`. Кастомный валидатор проверяет длину 2–150 UTF-16 единиц после `strip()`: это правило описано текстом, поскольку JSON Schema считает Unicode code points и не выполняет Java `strip()`. Дата рождения должна быть раньше текущей даты по часам Bean Validation; ограничения минимального возраста нет. Телефон соответствует `^[+]380[0-9]{9}$`: префикс `+380` и ровно 9 ASCII-цифр после него.

`verificationStatus` пока не реализован. Маппер всегда передаёт `null`; схема описывает именно это значение. Enum статусов и будущие модули верификации не добавлены. `completion.complete` вычисляется по наличию персональных данных и документов, а не по их верификации или подтверждению email.

## Ответы и сериализация

- `200` — профиль. Текущие MVC converters поддерживают JSON и YAML. В JSON даты имеют вид `YYYY-MM-DD`, в YAML — `[год, месяц, день]`; для этих представлений предусмотрены разные схемы.
- `204` — PUT успешно обновил персональные данные; тела ответа нет.
- `400` — PUT: `ApiProblem` с ошибками полей при Bean Validation; стандартный MVC `ProblemDetail` при отсутствии тела, некорректном JSON или нечитаемой дате.
- `401` — пустое тело и `WWW-Authenticate` от Spring Security. Это не `ApiProblem`.
- `404` — `ApiProblem`, если локальный профиль отсутствует.
- `406` — GET: стандартный `ProblemDetail`, если запрошено неподдерживаемое представление.
- `415` — PUT: стандартный MVC `ProblemDetail` для неподдерживаемого типа тела запроса.
- `500` — `ApiProblem` с безопасным сообщением для неожиданного исключения.

GET не имеет валидируемого ввода. Для PUT описаны ошибки валидации через общий `ApiError`. Уникальность телефона обеспечивает БД: отдельного обработчика конфликта нет, поэтому нарушение UNIQUE сейчас возвращает общий `500`, а не `409`. При ошибке транзакция обновления откатывается. Для PUT документировано JSON-тело запроса; обработка запроса другими конвертерами отдельно не проверялась.

Тексты ошибок пока заданы только на английском в `messages.properties`. Сообщения полей разрешаются через ключи вида `NotNull.updatePersonalInfoRequest.birthDate`, без `message` в аннотациях DTO. Например, отсутствие даты рождения возвращает `Date of birth is required.`. Одна проверка может вернуть несколько ошибок для поля; порядок ошибок не гарантирован. Заголовки и описания стандартных MVC-ошибок берутся из ключей `problemDetail.title.<exception>` и `problemDetail.<exception>`. Примеры `400`, `406` и `415` в спецификации обновлены под эти сообщения.

Неявный HEAD для GET, автоматический OPTIONS, служебные маршруты Spring Boot/Spring Security, RabbitMQ listeners и исходящие обращения к Keycloak не посчитаны отдельными REST-операциями модуля user.

## Проверка

Оба файла проверяются `openapi-spec-validator` 0.9.0 с `OpenAPIV31SpecValidator`. Дополнительно проверяются YAML без повторяющихся ключей, все `$ref`, покрытие двух операций, поля DTO запроса и примеры по JSON Schema Draft 2020-12.

Пять JSON-примеров проверены по схемам через JSON Schema Draft 2020-12. Временный тест MockMvc выполнил десять сценариев: два JSON-профиля, YAML-профиль, неподдерживаемый Accept, отсутствие авторизации, невалидный токен, некорректный bearer token, отсутствие профиля с двумя Accept и внутренняя ошибка. Полученные тела ответов сверены со схемами. Использованы реальные контроллер, security filters, advice, MapStruct mapper и evaluator; сервис профиля и JwtDecoder подменены. Подключение к PostgreSQL и живому Keycloak не выполнялось. Проверочные инструменты и тест размещены только в `target/openapi-validation`.

## Источники и границы достоверности

Основные источники: `ClientProfileController`, DTO в `user/web/dto/client/profile`, `ValidPersonName`, `PersonNameValidator`, `ClientProfileServiceImpl`, мапперы, `ProfileCompletionEvaluator`, `IdentityDocumentType`, `ProfileSection`, `SecurityConfig`, `CustomClaimValidator`, оба общих advice, `ApiProblemFactory`, `application.yaml` и `messages.properties`. Для PUT текущая проверка статическая; runtime-сценарии ниже относятся к ранее проверенному GET.

В локальных исходниках автоконфигурации Spring Boot 4.1.1 подтверждено, что beans `OAuth2TokenValidator<Jwt>`, включая `CustomClaimValidator`, добавляются к стандартным валидаторам JwtDecoder. Поэтому проверка UUID в `sub` учтена без предположения о необходимости дополнительного ручного подключения.

Неопределённости ограничены окружением и будущей реализацией:

- Адрес сервера, context path, JWT issuer/audience, Jackson-настройки и тексты ошибок могут быть переопределены внешней конфигурацией. Спецификация отражает текущие локальные настройки.
- Значения будущего `verificationStatus` пока не определены; текущий контракт допускает только `null`.
- URI типов ошибок используют `https://api.carhub.com/errors/...`, заданный в `ApiProblemFactory` и `CustomClaimValidator`. Наличие документации по этим адресам не подтверждено.
- Поведение реальных внешних систем не проверялось; результаты MockMvc подтверждают HTTP-слой и сериализацию в текущем наборе зависимостей.
